## 4. Bounding frame age (the safety rule: no advice from a stale frame)

Today every glasses frame is `.unknownDAT` and can never get a permit (`native/ChessCompanionCapture/README.md`). That must not change until one
of these methods is validated on real hardware.

1. **On-screen nonce (strongest, screen boards only).** The phone, or the screen showing the board, displays a code that changes several
   times a second, and the phone logs when each code was shown. A frame showing code N was captured no earlier than that code's display time,
   so the frame's true age is at most "now minus display time of N". This is a real upper bound in phone time.
   - Failure modes: misread or blurred codes (must abstain); display refresh lag (add a margin); unusable on a physical board; the code must never be confused with a chess square.
   - The mock *can* validate code drawing into the test video, reading it back, abstaining on unreadable codes, and the gate logic.
   - The mock *cannot* validate the timing: the file was encoded beforehand, so there is no live phone-time relationship.
2. **Learned clock offset from timestamps (monitoring, not a gate on its own).** Track `phone receipt time − frame timestamp`. The smallest
   value in a sliding window approximates "fixed offset + fastest delivery". A frame whose value rises above that minimum by more than X ms
   is late (a queue built up) and is rejected.
   - Failure modes: it measures delay only *relative to the fastest frame*, never absolute age. It breaks if timestamps reset on
     reconnect, fold or doff, if the clocks drift, or if timestamp meaning changes (#347).
   - The mock *can* validate timestamp monotonicity, behaviour across fold, doff and power cycles, and detection of delay injected in our own adapter.
   - The mock *cannot* validate real radio latency, clock drift or the glasses' timestamp semantics.
3. **Measured latency budget plus liveness.** Measure end-to-end latency once on hardware (glasses filming a phone stopwatch), set
   `budget = measured worst case + margin`, and accept a frame only if `(now − receipt) + budget ≤ limit`. Frames must keep arriving with no
   gap longer than G, and two consecutive agreeing frames are required.
   - Failure modes: a one-time measurement is no guarantee; frames that back up and arrive late, for example while the glasses microphone
     is active over Bluetooth (reported on Android: [#159](https://github.com/facebook/meta-wearables-dat-android/issues/159)); fewer usable frames.
   - The mock *can* validate the gap watchdog, the two-frame rule and fail-closed paths.
   - The mock *cannot* validate the budget value itself.

**Recommendation:** use (1) as the gate for screen-board practice, use (2) and (3) as extra fail-closed checks, and keep
real-glasses frames at "no permit" until a hardware run (a separate approval) gives numbers.
